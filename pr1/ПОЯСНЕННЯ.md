# ПР1. Пояснення до рішень

Шпаргалка до здавання: що зроблено, чому саме так, і відповіді на контрольні запитання.

## Як влаштовано застосунок

```
браузер ──► /api/weather?city=…  (app/main.py, веб-рівень)
                 │
                 ▼
        weather.get_current_weather(city)   (app/weather.py, інтеграція)
                 │
        ┌────────┴─────────┐
        ▼                  ▼
   геокодування        прогноз
   (назва → координати) (координати → погода)
```

- `app/weather.py` — єдиний файл, який імпортує `requests`. Назовні він віддає або словник із погодою, або виняток `WeatherError`.
- `app/main.py` — вирішує лише, який HTTP-статус і який JSON отримає клієнт. Про `requests`, URL-и Open-Meteo та їхні коди не знає нічого.
- `app/templates/index.html` — форма й показ результату або тексту помилки.

## Ухвалені рішення

### 1. Параметри запиту

Параметри передаються словником: `requests.get(url, params={...}, timeout=...)`. Бібліотека сама екранує значення — «Кривий Ріг» (пробіл), кирилицю, символи `&` чи `#` у вводі користувача. Якби URL склеювався рядком, назва міста з `&` зламала б запит або підмінила б інший параметр.

Геокодування: `name`, `count=1` (потрібен лише найкращий збіг), `language=uk`, `format=json`.
Прогноз: `latitude`, `longitude`, `current=temperature_2m,wind_speed_10m`.

### 2. Timeout

`TIMEOUT = (3.05, 10)` — 3 секунди на встановлення з'єднання, 10 секунд на очікування відповіді. Без timeout `requests` чекає нескінченно, і запит користувача «висне» разом із робочим потоком сервера.

Коли timeout спрацював, запит **не повторюється** автоматично: користувач уже чекав 10 секунд, а повтор подвоїв би очікування. Він отримує статус `504` і текст «Сервіс погоди не відповів вчасно. Спробуйте ще раз пізніше».

### 3. Типи помилок і HTTP-статуси

Одного `WeatherError` недостатньо: різні збої потребують різних статусів і різних повідомлень.

| Що сталося | Виняток у `weather.py` | Статус застосунку |
|---|---|---|
| Порожня або надто довга назва | `InvalidCityError` | `400` |
| Місто не знайдено | `CityNotFoundError` | `404` |
| Timeout | `ServiceTimeoutError` | `504` |
| Немає мережі, `5xx`, `429` від сервісу | `ServiceUnavailableError` | `503` |
| `4xx` від сервісу, не JSON, немає полів | `UnexpectedResponseError` | `502` |
| Будь-що непередбачене | — | `500` |

Відповідність «виняток → статус» лежить у `main.py` (таблиця `ERROR_STATUSES`), бо HTTP-статус власного застосунку — це рішення веб-рівня, а не модуля інтеграції.

Тіло помилки завжди однакове: `{"error": "<код>", "message": "<текст для користувача>"}`.

### 4. Різниця між 4xx і 5xx

- **5xx** — збій на боці Open-Meteo. Наш запит правильний, виправляти нічого; користувачеві кажемо «спробуйте пізніше» (`503`). Так само трактується `429` — сервіс просить зачекати.
- **4xx** — сервіс відхилив запит. Але параметри складає наш код, а не користувач, тож це **дефект застосунку**. Причину з поля `reason` пишемо в журнал сервера для розробника, а користувачеві показуємо нейтральний текст (`502`). Текст на кшталт `Parameter 'latitude' and 'longitude' must have the same number of elements` користувачеві нічого не скаже і розкриває внутрішню будову.

Клієнтові в обох випадках повертається 5xx, а не 4xx: він ввів коректну назву міста, проблема не в його запиті.

### 5. Місто не знайдено і несподіваний формат

Коли міста немає, Open-Meteo відповідає `200` і JSON **без ключа `results`** (див. `samples/geocoding-not-found.json`). Тому поле читається через `data.get("results")`, а відсутнє поле або порожній список означає `CityNotFoundError`.

Усе інше перевіряється явно, перш ніж використовувати:

- тіло не розібралося як JSON або це не об'єкт → `UnexpectedResponseError`;
- `results` не список, у першому елементі немає числових `latitude`/`longitude` → `UnexpectedResponseError`;
- немає об'єкта `current` або в ньому `temperature_2m`/`wind_speed_10m` не числа (зокрема `null`) → `UnexpectedResponseError`;
- немає `current_units` → **не помилка**: значення правильні, підставляються одиниці за замовчуванням (`°C`, `km/h`).

Порожній рядок перевіряється ще до звернення до мережі — немає сенсу витрачати запит.

### 6. Що модуль віддає назовні

Плоский словник: `city`, `country`, `latitude`, `longitude`, `temperature`, `temperature_unit`, `wind_speed`, `wind_speed_unit`, `time`. Назви полів Open-Meteo (`temperature_2m`, `current`) назовні не виходять — якщо колись змінити постачальника погоди, зміниться лише `weather.py`.

Координати беруться з геокодування, а не з відповіді прогнозу: прогноз повертає вузол сітки сервісу (`50.4375, 30.5` замість `50.45466, 30.5238`).

### 7. Сторінка

- Показує місто з країною, температуру й швидкість вітру; `km/h` перекладається на «км/год».
- При помилці показує поле `message` з відповіді сервера червоним.
- Дані вставляються через `textContent`, а не `innerHTML` — назва міста приходить ззовні й не повинна виконуватися як розмітка.
- Рядок із самих пробілів відсікається ще в браузері (атрибут `required` його пропускає).

## Як перевірити

Запуск:

```bash
uvicorn app.main:app --reload
```

Що ввести на сторінці http://127.0.0.1:8000:

| Ввід | Очікуваний результат |
|---|---|
| `Київ`, `Львів`, `Bratislava`, `Кривий Ріг` | погода |
| `Абвгдеж` | «Місто «Абвгдеж» не знайдено. Перевірте назву.» |
| порожньо або пробіли | «Введіть назву міста.» |
| вимкнути Wi-Fi і ввести `Київ` | «Сервіс погоди зараз недоступний…» |

Статуси видно напряму: http://127.0.0.1:8000/api/weather?city=Абвгдеж → `404`, http://127.0.0.1:8000/api/weather?city= → `400`.

Перевірка модуля без мережі, на збережених відповідях із `samples/` (17 тестів: успіх, місто не знайдено, timeout, недоступність, `4xx`/`5xx`, не JSON, відсутні поля):

```bash
python -m unittest discover -s tests -v
```

## Контрольні запитання

**1. Чому параметри краще передавати структуровано, а не склеювати в URL вручну?**
Бібліотека сама екранує значення, тож пробіли, кирилиця й службові символи (`&`, `=`, `#`, `?`) не ламають запит і не дають користувачеві підмінити чужий параметр. Запит легше читати й змінювати: додати параметр — це один рядок у словнику.

**2. Навіщо задавати timeout і як поводитися, коли він спрацював?**
Без нього запит може чекати нескінченно й блокувати сервер. Коли спрацював — перехопити `requests.Timeout`, не «падати», повідомити користувача зрозумілим текстом і повернути `504`. Повторювати автоматично варто лише обмежену кількість разів і з паузою; тут повтору немає, щоб не подвоювати очікування.

**3. Як по-різному реагувати на 4xx і 5xx?**
`5xx` — тимчасова проблема сервісу: запит правильний, можна спробувати пізніше. `4xx` — запит неправильний, повтор нічого не дасть, треба виправляти запит; якщо його склав наш код — це наш дефект, який записується в журнал.

**4. Чому інтеграцію виносять в окремий модуль?**
Веб-рівень працює з готовим результатом або зрозумілою помилкою й не залежить від HTTP-клієнта та формату чужого API. Змінити постачальника даних, додати кеш чи повтори можна в одному файлі. Модуль легко перевірити окремо, підмінивши відповіді збереженими зразками.

**5. Які збої можливі під час звернення до зовнішнього API і як їх обробити?**
Немає мережі або не розв'язалося ім'я (`ConnectionError`), timeout, `5xx`, `429`, `4xx`, тіло не JSON, JSON без очікуваних полів або з `null`, «успішна» відповідь без результату (місто не знайдено). Кожен перехоплюється в модулі інтеграції й перетворюється на власний тип помилки; веб-рівень зіставляє його з HTTP-статусом.

**6. Як цей самий підхід перенесеться на виклик AI API?**
Так само: окремий модуль, який знає адресу, ключ, формат запиту й відповіді моделі; обов'язковий timeout (моделі відповідають довго, тож він більший); розрізнення `4xx` (поганий запит, невірний ключ), `429` (ліміт — зачекати й повторити) і `5xx`; перевірка, що у відповіді справді є очікуване поле з текстом; веб-рівень отримує готовий текст або зрозумілу помилку.
